This lecture fills in the Lecture 8 templates with a complete, working UVM testbench for a 4 bit adder. Every piece is short, so it is the best place to see how the parts fit and where data flows.

Step 1Lab 2 recap

Lab 2 was the scaffolding. It had a top, a package, a test and two components whose phases mostly printed messages. It showed the phase order without doing any real checking. This lecture puts real content into each placeholder.

Step 2The DUT and its interface

Pseudocode
adder_if bundles:
    a and b   4 bits each
    sum       5 bits, so the carry out fits
Show the SystemVerilog
interface adder_if;
  logic [3:0] a;
  logic [3:0] b;
  logic [4:0] sum;     // 5 bits, so the carry out fits
endinterface

The adder is the ripple carry adder from Lecture 1. Four full adders are chained, each carry out feeding the next carry in, and the last carry out becomes sum[4].

Pseudocode
full_adder:
    sum       = a XOR b XOR carry_in
    carry_out = 1 when at least two of a, b, carry_in are 1

adder: chain four full adders
    bit 0 gets carry_in 0
    each next bit takes the previous bit's carry_out
    the last carry_out becomes sum bit 4
Show the SystemVerilog
module full_adder (output sum, output c_out, input a, input b, input c_in);
  assign sum   = a ^ b ^ c_in;
  assign c_out = (a & b) | ((a ^ b) & c_in);
endmodule

module adder (adder_if vif);
  wire [3:0] c_out;
  full_adder f_ad0 (vif.sum[0], c_out[0], vif.a[0], vif.b[0], 1'b0);
  full_adder f_ad1 (vif.sum[1], c_out[1], vif.a[1], vif.b[1], c_out[0]);
  full_adder f_ad2 (vif.sum[2], c_out[2], vif.a[2], vif.b[2], c_out[1]);
  full_adder f_ad3 (vif.sum[3], vif.sum[4], vif.a[3], vif.b[3], c_out[2]);
endmodule

Step 3The sequence item

The transaction holds two random inputs and the result.

Pseudocode
adder_item: random a and b, plus sum

do_copy(rhs):
    turn the general handle into an adder_item handle
        (report an error and stop if that is impossible)
    copy the parent's fields
    copy a, b and sum

convert2string:
    give back text like "A=3, B=4 | Sum=7"
Show the SystemVerilog
class adder_item extends uvm_sequence_item;
  `uvm_object_utils(adder_item)
  rand logic [3:0] a;
  rand logic [3:0] b;
  logic [4:0] sum;

  function new(string name = "adder_item"); super.new(name); endfunction

  virtual function void do_copy(uvm_object rhs);
    adder_item rhs_;
    if (!$cast(rhs_, rhs)) begin
      `uvm_error("ITEM_COPY", "Cast failed in do_copy")
      return;
    end
    super.do_copy(rhs);
    this.a = rhs_.a; this.b = rhs_.b; this.sum = rhs_.sum;
  endfunction

  virtual function string convert2string();
    return $sformatf("A=%0d, B=%0d | Sum=%0d", a, b, sum);
  endfunction
endclass
  1. do_copy is the hook UVM calls when anyone runs copy() or clone() on this item. It receives a uvm_object handle, so it uses $cast to get an adder_item handle, the downcast from Lectures 9 to 11.
  2. convert2string returns a readable string. $sformatf formats text like $display but returns it instead of printing.

Step 4The sequence

The sequence makes 10 random items. start_item waits until the driver is ready, and finish_item hands the item over and waits for item_done.

Pseudocode
body, repeat 10 times:
    create an item
    wait for the driver to be ready
    randomize it   (error if that fails)
    send it
Show the SystemVerilog
class adder_sequence extends uvm_sequence #(adder_item);
  `uvm_object_utils(adder_sequence)
  function new(string name = "adder_sequence"); super.new(name); endfunction

  virtual task body();
    adder_item item;
    repeat (10) begin
      item = adder_item::type_id::create("item");
      start_item(item);
      if (!item.randomize()) `uvm_error("SEQ", "Randomization failed!")
      finish_item(item);
    end
  endtask
endclass

The sequencer itself needs no custom code. The agent simply uses uvm_sequencer #(adder_item).

Step 5The driver

The driver gets the virtual interface from the config database, then loops. It takes an item, puts a and b on the pins, waits 10 time units for the combinational adder to settle, and reports done.

Pseudocode
forever:
    take the next item
    put a and b on the pins
    wait 10 time units for the adder to settle
    report done
Show the SystemVerilog
virtual task run_phase(uvm_phase phase);
  adder_item item;
  forever begin
    seq_item_port.get_next_item(item);
    vif.a = item.a;
    vif.b = item.b;
    #10;                           // time for the math and the sampling
    seq_item_port.item_done();
  end
endtask

There is no clock here because the adder is purely combinational, so the testbench paces itself with delays.

Step 6The monitor

The monitor also waits 10 time units per item, then builds a fresh item from whatever is on the pins and broadcasts it through an analysis port.

Pseudocode
item_collected_port: a broadcast port, built in new

forever:
    wait 10 time units
    create a fresh item
    copy a, b and sum off the pins
    broadcast it to every listener
Show the SystemVerilog
uvm_analysis_port #(adder_item) item_collected_port;   // built in new()

virtual task run_phase(uvm_phase phase);
  adder_item item;
  forever begin
    #10;
    item = adder_item::type_id::create("item");
    item.a   = vif.a;
    item.b   = vif.b;
    item.sum = vif.sum;
    item_collected_port.write(item);
  end
endtask

Note that analysis ports are built with new in the constructor, not with the factory.

Step 7The agent

The agent builds the driver, monitor and sequencer, then connects the driver's seq_item_port to the sequencer's seq_item_export.

Step 8The predictor, a reference model

The predictor extends uvm_subscriber, which gives it a ready made analysis_export and asks for one write() function. Whenever the monitor broadcasts, write() runs automatically.

Pseudocode
whenever the monitor broadcasts an item t:
    make a copy of t       (never change the original)
    expected sum = a + b
    send the copy to the scoreboard
Show the SystemVerilog
virtual function void write(adder_item t);
  adder_item expected_item;
  $cast(expected_item, t.clone());   // copy, so the monitor's item is untouched
  expected_item.sum = expected_item.a + expected_item.b;
  results_port.write(expected_item);
endfunction

clone() builds a new object and copies into it using do_copy. It returns a uvm_object handle, so $cast is needed again.

Step 9The scoreboard

The scoreboard receives two streams, actual results from the monitor and expected results from the predictor. A component can only define one function named write, so the macro uvm_analysis_imp_decl creates two renamed versions.

Pseudocode
two separate inputs:
    actual     from the monitor
    expected   from the predictor
two queues to hold them

new: build both inputs

write_actual(item):    add it to the actual queue, then try to compare
write_expected(item):  add it to the expected queue, then try to compare

compare:
    if both queues have something:
        take the oldest item from each
        if the sums match exactly:  report MATCH
        otherwise:                  report MISMATCH as an error
Show the SystemVerilog
`uvm_analysis_imp_decl(_actual)
`uvm_analysis_imp_decl(_expected)

class adder_scoreboard extends uvm_scoreboard;
  `uvm_component_utils(adder_scoreboard)
  uvm_analysis_imp_actual   #(adder_item, adder_scoreboard) actual_imp;
  uvm_analysis_imp_expected #(adder_item, adder_scoreboard) expected_imp;
  adder_item actual_q[$], expected_q[$];

  function new(string name = "adder_scoreboard", uvm_component parent = null);
    super.new(name, parent);
    actual_imp   = new("actual_imp", this);
    expected_imp = new("expected_imp", this);
  endfunction

  virtual function void write_actual(adder_item item);
    actual_q.push_back(item);   compare_data();
  endfunction

  virtual function void write_expected(adder_item item);
    expected_q.push_back(item); compare_data();
  endfunction

  virtual function void compare_data();
    if (actual_q.size() > 0 && expected_q.size() > 0) begin
      adder_item act = actual_q.pop_front();
      adder_item exp = expected_q.pop_front();
      if (act.sum === exp.sum) `uvm_info("SB_PASS", "MATCH", UVM_LOW)
      else                     `uvm_error("SB_FAIL", "MISMATCH")
    end
  endfunction
endclass

The two queues line the streams up in order, and === compares including X and Z, so an X on the DUT output counts as a mismatch.

Step 10Environment, test and top

The environment builds the agent, predictor and scoreboard, then makes three connections.

  1. Monitor port to the predictor's analysis_export.
  2. Monitor port to the scoreboard's actual_imp.
  3. Predictor results_port to the scoreboard's expected_imp.

One analysis port feeds two listeners, which is exactly what analysis ports are for.

The test raises an objection, starts the sequence on env.agent.sequencer, waits 10 more time units so the last item gets checked, and drops the objection.

Pseudocode
top:
    make the interface and connect the adder to it
    store the interface in the config database for everyone ("*")
    start adder_test
Show the SystemVerilog
module top;
  adder_if inf();
  adder dut (.vif(inf));
  initial begin
    uvm_config_db #(virtual adder_if)::set(null, "*", "vif", inf);
    run_test("adder_test");
  end
endmodule

Here the path is "*", so every component can get vif directly.

Step 11Catching a planted bug

The last slide changes one connection. Stage 2 takes c_out[0] as its carry in instead of c_out[1]. The scoreboard then reports MISMATCH for inputs where those two carries differ. That is the whole point, a wiring mistake found automatically, without anyone checking waveforms.

Traps to watch for

  • Modifying the monitor's item in the predictor instead of a clone. The expected and actual items would become the same object and every check would pass.
  • Dropping the objection right after the sequence, before the last result is compared.
  • Two write functions in one component without uvm_analysis_imp_decl.

Practice

Try each one first, then open the answer.

  1. Why is sum 5 bits wide while a and b are 4 bits?
    Show answer

    Two 4 bit numbers can add to at most 30, which needs 5 bits.

  2. With a = 9 and b = 8, what does the predictor put in sum, in decimal and binary?
    Show answer

    17, which is 5'b10001.

  3. Why does the monitor wait #10 before sampling?
    Show answer

    The driver applies inputs and the combinational logic needs time to settle before the sum is valid.

  4. In the bugged adder, find the DUT output for a = 2 and b = 2. Does the scoreboard pass or fail?
    Show answer

    Bit 1 makes a carry, but stage 2 takes carry 0, which is 0. The DUT outputs 0 instead of 4, so the scoreboard fails.

  5. Give one input pair that passes even with the bug, and explain why.
    Show answer

    a = 3 and b = 0. No stage makes a carry, so c_out[0] and c_out[1] are both 0 and the wrong wire carries the right value.

  6. Why must the predictor work on t.clone() instead of t?
    Show answer

    The monitor's item is also going to the scoreboard. Changing it would change the actual value, and the comparison would test nothing.

  7. Add a functional coverage subscriber that covers a and b with 4 bins each and their cross. Show its write().
    Show answer

    One version is below.

    Pseudocode
    adder_cov listens to the monitor

covergroup:
    a sorted into 4 bins
    b sorted into 4 bins
    every (a bin, b bin) pair, 16 in all

new:       build the covergroup
write(t):  remember t, take a coverage snapshot
    Show the SystemVerilog
    class adder_cov extends uvm_subscriber #(adder_item);
  `uvm_component_utils(adder_cov)
  adder_item it;
  covergroup cg;
    cp_a : coverpoint it.a { option.auto_bin_max = 4; }
    cp_b : coverpoint it.b { option.auto_bin_max = 4; }
    axb  : cross cp_a, cp_b;
  endgroup
  function new(string name, uvm_component parent);
    super.new(name, parent);
    cg = new();
  endfunction
  virtual function void write(adder_item t);
    it = t;
    cg.sample();
  endfunction
endclass
